🌱 Sustainability: what keeps these pages running

TL;DR: Nothing here costs money. What keeps these pages alive is a short list: one deploy key that publishes them, a daily rebuild, the kit they carry inside them, and link previews that other apps keep for a while. Each is written down below, with what to do when it needs attention.

This AstroLog is one public site built from two repositories. This page lists what each one needs, so none of it depends on anyone’s memory. It’s also the repository’s SUSTAINABILITY.md, so it reads the same on GitHub.

The pieces

Repository What it is How it goes live
changelog-astro (private) The source: entries, drafts, write-ups, the Astro site A workflow builds it and publishes only the finished pages
changelog-astro-public (public) The built AstroLog you’re reading GitHub Pages, straight from what the workflow pushes to main

What can quietly stop, and what to do

🔑 The deploy key (CHANGELOG_ASTRO_PUBLIC_DEPLOY_KEY)

The workflow in the private source pushes the finished pages into changelog-astro-public with a deploy key: a key that can write to that one repository and nothing else. Its private half is the Actions secret CHANGELOG_ASTRO_PUBLIC_DEPLOY_KEY on changelog-astro; its public half sits in the twin’s Settings › Deploy keys. Deploy keys don’t expire, and no personal token is involved. Until the key exists, the workflow does nothing and says so.

What to do: an owner of the organisation runs sh scripts/setup-lane-keys.sh in this repository, once. Running it again makes a fresh key and replaces the secret; the old key can then be removed in the twin’s Deploy keys.

🗓️ The daily rebuild

The ledger lists every public change to his home in plain words, read from GitHub when the site is built. So it stays fresh on days nothing else changes, the workflow also runs every day at 10:23 UTC. It uses a few minutes of the organisation’s Actions allowance a day. If GitHub’s API has a bad moment, the build falls back to a committed snapshot (astro/src/data/ledger.snapshot.json) and still publishes.

What to do: if the ledger’s newest day looks old, open the workflow’s run history. To refresh the snapshot by hand: cd astro && npm run ledger:snapshot.

🧰 The kit is carried inside

The look, the welcome, the menus, / search, the contact and community windows and the map’s cards all come from the arrival kit (1.5.2): arrival.js and arrival.css, copied unchanged into astro/public/arrival/, with this home’s own org.js (facts and links) and org.css (his colours). His website draws its own welcome its own way, so this AstroLog carries the kit itself instead of borrowing it. The fonts (Poppins, JetBrains Mono) and icons (Phosphor) are served from these pages too: nothing loads from another site.

What to do: to upgrade, copy the kit files unchanged from my-template/changelog-template/arrival/, read its notes, and rebuild.

🖼️ Cached link previews

Every page has its own share picture, built with the site. Messaging apps keep their own copy of a link’s preview for days or weeks, so after a picture changes, old previews linger. Cards never carry counts, so a cached one doesn’t go stale on its own.

🔒 What is turned off, on purpose

Giving, a pledge and any wallet connection are off: no wallet address is ever supplied by a helper. There is no analytics and no cookie. No one’s email is used for a picture. Search engines are asked not to list the pages. Each of these is TMade Alex’s to change.

🤝 Who holds the keys today

The member of his community who set the home up is, for now, the organisation’s owner, and the one who runs the key script above. When TMade Alex accepts the invitation to his organisation, he is an owner too, and the keys are his.
